### **أولاً: التقنيات والمكتبات الأساسية (The Next.js Core Stack)**

قبل تفصيل المتطلبات، سنعتمد على الميزات والآليات التالية في Next.js:

1. **App Router:** لإدارة هيكلة المسارات بشكل هرمي واحترافي.  
2. **Server Components:** لتقليل حجم الـ Bundle وحماية الـ Data Fetching.  
3. **Server Actions:** لإدارة العمليات الخلفية (Forms & DB Mutations) بشكل آمن.  
4. **Optimized Image Component:** للتعامل مع صور المصورين والمعارض.  
5. **Caching & Revalidation:** لتحسين أداء التقارير والبيانات المتكررة.

### **ثالثاً: تفصيل آليات التنفيذ لكل فئة متطلبات**

#### **1\. متطلبات العميل (Client & Visitor)**

* **تصفح المتجر والخدمات (FR-V1, V2):** سنستخدم **Server Components** لجلب البيانات مباشرة من السيرفر. هذا يضمن أن البيانات تكون جاهزة للزاحف (SEO) وبسرعة تحميل فائقة.  
* **سلة المشتريات (FR-C5):** سنستخدم **Zustand** لأنه خفيف جداً، مع تخزين الحالة في localStorage لضمان بقاء المنتجات في السلة عند تحديث الصفحة.  
* **الحجز (FR-C3, C4):** سنستخدم **Server Actions** داخل الـ App Router. هذه الآلية تضمن تنفيذ التحقق من المواعيد (Validation) في السيرفر قبل أي تفاعل مع قاعدة البيانات، مما يمنع التلاعب.

#### **2\. متطلبات المصور (Photographer)**

* **الجدول والمهام (FR-P2, P3):** سنستخدم **React Query** لجلب البيانات. لماذا؟ لأنها تدعم التحديث اللحظي (Polling أو Mutations) إذا تغيرت حالة الحجز من قبل المدير.  
* **رفع الصور (FR-P5):** سنستخدم **Next.js API Routes** (أو Server Actions) للتعامل مع الـ File Streams، مع مكتبة **Sharp** لضغط الصور (Optimization) قبل حفظها.

#### **3\. متطلبات المدير (Administrator)**

* **لوحة التحكم والتقارير (FR-A6):** سنستخدم **Recharts** (مكتبة React قوية ومتجاوبة) لعرض الرسوم البيانية. البيانات سيتم جلبها عبر Server Components لتكون سريعة جداً.  
* **تصدير البيانات (FR-A10):** سنستخدم **xlsx** (لـ Excel) و **pdfmake** أو **jsPDF** (لـ PDF)؛ تتم معالجة هذه الطلبات في السيرفر لتقليل الضغط على المتصفح.

#### **4\. المتطلبات غير الوظيفية (NFRs)**

* **الأمان (NFR-SEC):** سنستخدم الـ **Middleware** في Next.js للتأكد من هوية المستخدم (Role-based Authorization) في كل طلب (Request).  
* **التسامح مع الأخطاء (NFR-ET):** سنعتمد على **Global Error Handling** في Next.js (ملفات error.js و not-found.js) لتقديم واجهات احترافية بدلاً من الشاشات البيضاء أو الأخطاء البرمجية.

### **تفصيل آليات التنفيذ القياسية (Best Practices):**

#### **1\. أمن البيانات (Row Level Security \- RLS) \- الأهم عالمياً**

بدلاً من حماية البيانات في الكود فقط، سنستخدم **RLS** في Supabase.

* **مثال:** عند طلب المصور لجدوله (FR-P2)، نكتب سياسة في قاعدة البيانات تقول: *فقط المصور الذي يطابق photographer\_id في الصف هو من يمكنه قراءته*. هذا يجعل النظام محصناً حتى لو تم اختراق الكود\!

#### **2\. التفاعل بين Next.js و Supabase**

* **Server Actions:** سنقوم بكتابة جميع العمليات التي تعدل في البيانات (مثل createBooking) داخل ملفات actions.ts. هذه الدوال ستستخدم createClient الخاص بالخادم لتكون العمليات مؤمنة وتتم في بيئة السيرفر.  
* **Middleware:** سنستخدم middleware.ts في Next.js للتحقق من وجود الجلسة (Session) قبل السماح للمستخدم بالدخول لأي مسار (مثلاً /admin/\* أو /photographer/\*).

#### **3\. التعامل مع الوسائط (Storage)**

* **FR-P5 (رفع الصور):** لن نحفظ الصور في قاعدة البيانات. سنحفظها في **Supabase Storage** (كـ Buckets)، ونحفظ فقط "رابط الصورة" (Public URL أو Signed URL) في جدول المنتجات أو الجلسات. سنستخدم **Signed URLs** للصور الخاصة بالعملاء لضمان عدم وصول أي شخص للصور إلا العميل والمصور.

#### **4\. الإشعارات اللحظية (Realtime)**

* **FR-P6:** سنقوم بتهيئة "قناة" (Channel) في Supabase مرتبطة بجدول الإشعارات. المصور، بمجرد دخوله للوحة التحكم، يفتح اتصالاً لحظياً (WebSocket)، وفور إضافة المدير لحجز جديد، يظهر الإشعار للمصور دون الحاجة لإعادة تحميل الصفحة.

#### **5\. وظائف الذكاء الاصطناعي (Edge Functions)**

* **FR-C7:** عندما يقوم العميل باختيار جلسة، سنقوم باستدعاء **Supabase Edge Function** التي ستتحدث مع الـ API الخاص بـ Gemini، ثم تعيد النتيجة للواجهة في Next.js. سنستخدم **pgvector** في Supabase لتخزين "تفضيلات العميل" كـ (Embeddings) للبحث عن أكثر المنتجات تشابهاً مع اهتماماته.
